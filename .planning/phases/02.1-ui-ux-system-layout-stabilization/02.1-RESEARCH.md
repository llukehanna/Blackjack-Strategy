**Researched:** 2026-03-24

## Summary

This phase is a pure UI refactoring phase with no new features. The scope is well-defined: create design token files (Spacing, Typography, BJSColors), refactor 5 existing components to use them, fix tab bar / safe area bugs, and remove a redundant header. The codebase is small (9 view files, ~500 lines of view code total) and every change is specified in detail by CONTEXT.md and the UI-SPEC.

The primary technical challenges are: (1) correctly implementing adaptive custom colors in SwiftUI without an asset catalog, (2) fixing tab bar safe area clipping in a TabView > NavigationStack > content hierarchy, and (3) ensuring the primary/secondary action button split in ActionButtonsView correctly distinguishes Hit/Stand from Double/Split/Surrender without breaking the existing `ForEach` over `availableActions`.

**Primary recommendation:** Execute as a token-foundation-first approach: create the 3 design token files, then refactor each view file to use them, working from leaf components (CardView) inward to container views (TrainerView). Fix the tab bar safe area issue in TrainerView as a dedicated task since it requires understanding the TabView > NavigationStack layout stack.

### Pattern 1: Design Token Enums
**What:** Define spacing, color, and typography as enums with static properties. Enums with no cases prevent accidental instantiation.
**When to use:** Namespaced constants that should never be instantiated.
**Example:**
```swift
// Spacing.swift
enum Spacing {
    static let xs: CGFloat = 4
    static let sm: CGFloat = 8
    static let smd: CGFloat = 12
    static let md: CGFloat = 16
    static let lg: CGFloat = 24
    static let xl: CGFloat = 32
}

// BJSColors.swift
import SwiftUI

enum BJSColors {
    static let accent = Color(
        UIColor { traits in
            traits.userInterfaceStyle == .dark
                ? UIColor(red: 0.82, green: 0.85, blue: 0.88, alpha: 1.0)  // #D1D9E0
                : UIColor(red: 0.11, green: 0.17, blue: 0.23, alpha: 1.0)  // #1C2B3A
        }
    )
}

// Typography.swift
import SwiftUI

enum Typography {
    static let title: Font = .title2.bold()
    static let section: Font = .subheadline
    static let body: Font = .body
    static let secondary: Font = .subheadline
    static let mono: Font = .title2.monospaced().bold()
    static let buttonLabel: Font = .body.bold()
}
```

### Pattern 2: Adaptive Color via UIColor Dynamic Provider
**What:** Use `UIColor { traitCollection in ... }` wrapped in SwiftUI `Color()` for light/dark adaptive custom colors.
**When to use:** When a custom (non-system) color must adapt to dark mode.
**Why this approach:** Defining colors via `UIColor` dynamic provider is the standard way to create adaptive colors in code without an asset catalog. The alternative (Color asset catalog) was explicitly rejected by the user (D-04).

**Confidence:** HIGH -- This is the standard SwiftUI approach for dynamic colors without asset catalogs.

### Pattern 3: SectionContainerView for Consistent Layout
**What:** A reusable view or ViewModifier that applies consistent horizontal inset and vertical padding to section content.
**When to use:** SessionStartView sections that currently repeat `.padding(.horizontal, 16)` + `Divider()`.
**Example:**
```swift
struct SectionContainerView<Content: View>: View {
    let content: Content

    init(@ViewBuilder content: () -> Content) {
        self.content = content()
    }

    var body: some View {
        VStack(alignment: .leading, spacing: Spacing.sm) {
            content
        }
        .padding(.horizontal, Spacing.md)
        .padding(.vertical, Spacing.md)
    }
}
```

### Pattern 4: Primary/Secondary Button Classification
**What:** In ActionButtonsView, classify actions as primary (Hit, Stand) or secondary (everything else) and apply different styling.
**When to use:** ActionButtonsView refactor.
**Key consideration:** The `Action` enum from BJSCore determines available actions. Hit and Stand are always present. Double, Split, Surrender are conditional. The split must be based on the action value, not position.
**Example:**
```swift
private func isPrimaryAction(_ action: Action) -> Bool {
    action == .hit || action == .stand
}
```

### Pattern 5: Tab Bar Safe Area Fix
**What:** Ensure content in TrainerView clears the tab bar.
**Key insight:** In the current architecture, `BJSApp` uses `TabView { Tab { NavigationStack { SessionStartView() } } }`. The `TrainerView` is pushed via `.navigationDestination`. When inside a `TabView`, the tab bar's safe area is automatically provided by the system. The issue is that `TrainerView` uses `VStack(spacing: 0)` with fixed spacers that may not account for the tab bar inset.

**Fix approach:** The bottom content (action buttons + "End Session") needs to be above the tab bar. Two options:
1. Ensure the bottom `Spacer(minLength:)` in playArea respects the safe area (it should by default)
2. Add `.padding(.bottom)` or `.safeAreaInset(edge: .bottom)` if the `VStack` clips

**Root cause analysis:** The `playArea` VStack uses `.padding(.bottom, 8)` which is likely insufficient. The tab bar safe area should be respected by default in a VStack, but the `Spacer(minLength: 24).fixedSize()` at the bottom may be forcing a fixed 24pt spacer that doesn't flex for the tab bar. The `.fixedSize()` modifier is the likely culprit -- it prevents the Spacer from growing to accommodate the safe area.

**Confidence:** HIGH -- Removing `.fixedSize()` from the bottom Spacer in playArea should allow it to grow to accommodate tab bar safe area. If not, adding explicit bottom padding equal to the tab bar height is the fallback.

### Anti-Patterns to Avoid
- **Raw number literals in padding/spacing:** Every `.padding(16)` must become `.padding(Spacing.md)`. Grep audit shows 28 raw padding occurrences across 5 files.
- **Inconsistent background colors:** SessionSummaryView uses `.secondarySystemBackground` while SessionStartView uses `.systemGroupedBackground`. The UI-SPEC normalizes both to `.systemGroupedBackground`.
- **Creating unused abstractions:** D-20 explicitly says no design system file that is not immediately used. Only extract components used in 2+ places.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Dark mode color adaptation | Manual `@Environment(\.colorScheme)` checks | `UIColor { traitCollection in ... }` dynamic provider | System handles trait changes automatically, works in previews |
| Tab bar safe area | Manual `.padding(.bottom, 83)` or similar hardcoded values | System safe area insets (remove `.fixedSize()` blocker) | Hardcoded values break across device sizes |
| Touch target sizing | Custom gesture areas | `.frame(minHeight: 44)` on buttons | Standard HIG approach, already in use |

## Common Pitfalls

### Pitfall 1: Color Asset vs Code-Defined Color
**What goes wrong:** Developers create a Color asset in the asset catalog when the user explicitly said Swift constants (D-04).
**Why it happens:** Asset catalog is the "default" Xcode approach.
**How to avoid:** Use `UIColor { traits in ... }` wrapped in `Color()`. Keep in `BJSColors.swift`.
**Warning signs:** `.xcassets` files modified in this phase.

### Pitfall 2: Accent Color Not Propagating to System Controls
**What goes wrong:** Setting `BJSColors.accent` but `.borderedProminent` buttons and segmented pickers still use the system blue.
**Why it happens:** SwiftUI `.borderedProminent` uses the `accentColor` / `.tint()` modifier, not arbitrary Color constants.
**How to avoid:** Set `.tint(BJSColors.accent)` on the app root or on each relevant view. Alternatively, set the app's accent color in the asset catalog (this is separate from the D-04 constraint which is about referencing colors as typed constants). The most reliable approach: add `.tint(BJSColors.accent)` to the `TabView` in `BJSApp.swift`.
**Warning signs:** Blue-tinted buttons despite defining a custom accent color.

### Pitfall 3: Tab Bar Safe Area in NavigationStack
**What goes wrong:** Content still clips behind the tab bar after changes.
**Why it happens:** The `VStack(spacing: 0)` in TrainerView body sits inside a NavigationStack inside a TabView. Safe area insets flow through this hierarchy, but `Spacer().fixedSize()` at the bottom of playArea prevents the spacer from growing.
**How to avoid:** Remove `.fixedSize()` from the bottom Spacer. If needed, add `.safeAreaInset(edge: .bottom)` with appropriate spacing.
**Warning signs:** "End Session" button partially hidden behind tab bar.

### Pitfall 4: Forgetting to Update XcodeGen project.yml
**What goes wrong:** New files (Design/Spacing.swift, etc.) exist on disk but are not included in the Xcode project.
**Why it happens:** XcodeGen generates the project from `project.yml`. The `sources: [BJS]` glob should pick up new files automatically.
**How to avoid:** Verify that `sources: [BJS]` in project.yml includes the new `BJS/Design/` directory. Since `[BJS]` is a directory glob, it should automatically include all `.swift` files under `BJS/`. After adding new files, run `xcodegen generate` to regenerate.
**Warning signs:** Build errors about missing files.

### Pitfall 5: Typography.section vs Typography.secondary Ambiguity
**What goes wrong:** Both `section` and `secondary` are defined as `.subheadline` with `.foregroundStyle(.secondary)`. Developers use them interchangeably.
**Why it happens:** They have the same font. The distinction is semantic, not visual.
**How to avoid:** `Typography` enum defines only the `Font` value. The `.foregroundStyle(.secondary)` is applied at the call site, not baked into the Typography constant. Document that `section` is for labels ("Mode", "Rules") and `secondary` is for supporting text.
**Warning signs:** Inconsistent usage of section vs secondary in code review.

### Pitfall 6: ActionButtonsView Primary/Secondary Split Breaking Layout
**What goes wrong:** Splitting Hit/Stand from Double/Split/Surrender into two HStacks changes the visual layout from a single row to potentially two rows.
**Why it happens:** The UI-SPEC shows all buttons in the same HStack with different styling, not separate rows.
**How to avoid:** Keep a single `HStack` or `FlowLayout`. Apply different fill/label colors based on `isPrimaryAction()` classification. Do not restructure the layout into multiple rows.
**Warning signs:** Buttons wrapping to two lines or appearing in separate groups.

### StatsBarView Redesign
```swift
// Source: UI-SPEC StatsBarView Redesign section
struct StatsBarView: View {
    let stats: SessionStats

    var body: some View {
        HStack(spacing: 0) {
            statChip(value: "\(Int(stats.accuracy))%", label: "Accuracy")
            thinDivider
            statChip(value: "\(stats.handCount)", label: "Hands")
            thinDivider
            statChip(value: "\(stats.errorCount)", label: "Errors")
        }
        .padding(.vertical, Spacing.sm)
        .frame(maxWidth: .infinity)
        .background(Color(.secondarySystemBackground))
        .overlay(alignment: .bottom) {
            Rectangle()
                .fill(Color(.separator))
                .frame(height: 0.5)
        }
    }

    private func statChip(value: String, label: String) -> some View {
        VStack(spacing: 2) {
            Text(value).font(.body.bold())
            Text(label).font(.caption).foregroundStyle(.secondary)
        }
        .frame(maxWidth: .infinity)
    }

    private var thinDivider: some View {
        Rectangle()
            .fill(Color(.separator))
            .frame(width: 0.5, height: 24)
    }
}
```
